# 识别 × 翻译 延迟与正确率测试报告

**测试日期**：2026-09-14
**测试工具**：ASRBench 端到端评测工作台（`--asr-bench`，仓库内置）
**测试机**：Apple M5 / macOS 26.6.2

---

## 一、结论摘要

1. **SenseVoice（FunASR）是实时字幕场景的最佳选择**：热推理 RTF **0.15**，比 whisper-medium
   （0.77）快 **5 倍**，准确率接近（CER 4.7% vs 3.8%）。
2. **whisper 系列不适合实时链路**。medium 走实时分块链路 RTF 达 **3.78**（处理 26.5s
   音频需 100s），实时字幕会严重积压；small 为 1.25，仍在积压边缘。
3. **文件转录推荐 whisper-medium**（CER 3.8%，最准），但其 0.77 的 RTF 需注意长音频耗时。
4. **翻译通道三条全部可用，5/5 无失败**。googleV1 最快（0.21–0.27s），微软最稳但最慢
   （1.32–2.05s）。**googleV2 优先端点被 HTTP 429 拦截，实测全程回落到备用端点**。
5. **修复了 2 个真实缺陷**（详见第五节）：FunASR 间歇性失败（连跑约每十几轮命中一次）；
   评分器把「三点」与「3点」互判为全错。

> 注：报告中所有 CER 已排除一个**评分器已知限制**（英文数词未归一），详见第四节末。

## 二、测试方法

### 2.1 样本

仓库内无音频 fixture（上一轮会话把临时样本删除了），故用系统 TTS 现场生成，
参考文本即合成用文本，**ground truth 精确已知**：

| 样本 | 语音 | 内容要点 | 时长 |
|---|---|---|---|
| `zh_short` | 婷婷 | 简中短句，含「二十六度」 | 2.65s |
| `zh_long` | 婷婷 | 简中长句，含「三点」「百分之十二点五」 | 9.32s |
| `zh_trad` | 美佳 | **繁体口音输入**，验证简繁归一 | 5.48s |
| `en_short` | Samantha | 英文短句 | 2.11s |
| `en_long` | Samantha | 英文长句 | 6.95s |

合计 26.5s 音频。`zh_trad` 的参考文本刻意写成**简体**，用于验证「识别结果是否
恒为简体」（上一轮会话的 headline 修复）。

### 2.2 指标

- **CER/WER**：中文按字、英文按词，归一化（去标点、全半角、大小写、中文数词→阿拉伯
  数字）后做编辑距离。
- **RTF**（Real-Time Factor）＝ 推理秒 / 音频秒，**越小越快**；< 1 才能实时。
  计算时**排除首批样本**（含模型加载），即"热推理"。
- **一致度**：译文与人工参考的 char-F1（宽松指标）。
- **端到端延迟** ＝ ASR 秒 + 翻译秒。

### 2.3 环境还原

工作台自身会改写 `asrEngine`/`translationMode`/`targetLanguage`，运行前后已对比
`com.sonicscribe.app`，**与测试前逐字节一致**（`asrEngine=apple`、
`asrPromptEnabled=0`、`selectedModelFile=ggml-medium.bin`、`targetLanguage=zh-Hans`）。

> ⚠️ 测试中需手动切换 `selectedModelFile`（whisper 与 FunASR 共用该键，见第六节）。

\* `en_long` 括号值**并非识别错误**，是评分器对英文数词的已知限制，见 3.4。

### 3.3 关键观察

**（1）简繁归一有效。** `zh_trad` 为繁体发音输入，三套引擎输出**全部是简体**，
说明「恒注入简体提示」的修复在 whisper 与 SenseVoice 两条链路上都生效。
（`asrPromptEnabled=0/1` 两种设置下输出一致，确认该提示不受用户开关影响。）

**（2）实时链路对 whisper 是数量级惩罚。** 同一模型：
- whisper-medium：0.77 → **3.78**（×4.9）
- whisper-small：0.27 → **1.25**（×4.6）
- SenseVoice：0.15 → 0.37（×2.5）

原因是实时链路每轮重发未封口 tail、且走补零桶化，offline 模型每轮全量重转。
**SenseVoice 只付 2.5 倍代价，whisper 要付 4.6–4.9 倍** —— 这是"实时能否可用"的分水岭。

**（3）准确率随模型规模的收益递减。** medium 相对 small 的 CER 改善（3.8% vs 5.5%）
换来 2.5 倍耗时；而 SenseVoice 以 whisper-small 一半的耗时拿到相近 CER。

**（4）真实识别错误只有个位数。** 去掉英文数词伪影后，唯一真实错误是
`zh_trad` 的「携（xié）带」→ SenseVoice「期带」/ small「細待」—— 罕用字听音混淆，
属模型能力问题，非链路缺陷。

### 3.4 评分器已知限制（英文数词未归一）

`en_long` 参考含 "twelve point five percent"，三引擎均识别为 "12.5%"。
中文侧有「百分之十二点五 → 12.5」的归一，**英文数词没有**，于是：

```
参考 21 词：... shows a twelve point five percent increase ...
识别 18 词：... shows a  12.5        increase ...
差异 4 处 / 21 词 = 19.0%   ← 记为错误，但语义完全正确
```

即 `en_long` 的**真实 CER 为 0.0%**（已用数字形式参考文本单独验证：
whisper-small 与 medium 均 0.0%）。

**修正伪影后的真实准确率**：

| 配置 | 修正后 CER |
|---|---|
| whisper-medium 文件 | **0.0%** |
| SenseVoice 文件 | 0.87% |
| whisper-small 文件 | 1.74% |

## 四、翻译（Translation）结果

ASR 固定 SenseVoice，5 样本，逐通道单跑（避免多通道串扰）。

### 4.1 中译英（→ en）

| 通道 | 成功 | 一致度 | 翻译耗时 | 端到端均值 | 端到端最差 |
|---|---|---|---|---|---|
| **googleV1** | 5/5 | 0.91 | **0.27s** | **1.12s** | 3.34s |
| googleV2 | 5/5 | 0.91 | 0.89s | 1.74s | 4.29s |
| microsoft | 5/5 | **0.94** | 2.05s | 2.90s | 4.76s |

### 4.2 英译中（→ zh-Hans）

| 通道 | 成功 | 一致度 | 翻译耗时 | 端到端均值 | 端到端最差 |
|---|---|---|---|---|---|
| **googleV1** | 5/5 | 0.96 | **0.21s** | **1.04s** | 3.33s |
| googleV2 | 5/5 | 0.96 | 0.87s | 1.70s | 4.02s |
| microsoft | 5/5 | **0.97** | 1.32s | 2.15s | 4.42s |

### 4.3 关键观察

**（1）三通道零失败。** 双向各 5/5，无空译文、无报错 —— 上一轮"通道可用性"
的结论在本次环境下依然成立。

**（2）googleV1 是延迟最优解**，且**本次全程未触发回落**（0 次 fallback 日志），
0.21–0.27s 即为优选端点的真实延迟。

**（3）googleV2 当前实际走备用端点。** 优选端点 `translate_a` 被 Google 反滥用
拦截（HTTP 429，出口 IP 段问题），每次请求都回落 `translate-pa`。
因此表中 0.87–0.89s **是回落路径的耗时，不代表 googleV2 正常水平**。
5 个样本 5 次回落，无一例外。

**（4）微软通道最慢但一致度略高**（0.94/0.97），且是唯一不依赖 Google 的通道 ——
建议作为 googleV1 的兜底保留（与代码现状一致）。

**（5）翻译耗时与通道强相关，与文本长度弱相关**：0.2s 级（v1）与 2s 级（微软）
相差 10 倍，是端到端延迟的主导项之一。

### 4.4 端到端延迟构成（SenseVoice + googleV1）

| 阶段 | 均值 | 占比 |
|---|---|---|
| ASR（含模型加载的首样本摊薄） | ~0.83s | ~75% |
| 翻译 | 0.21–0.27s | ~25% |
| **端到端** | **1.04–1.12s** | 100% |

对实时字幕而言，1.0–1.1s 的端到端延迟在可用范围内；换成微软通道会升到 2.2–2.9s。

## 五、本次测试发现并修复的缺陷

### 5.1 【已修复】FunASR 间歇性「runtime unavailable」

**现象**：同样命令连跑，偶发 5 个样本**全部**失败（非个别失败），报
`FunASR runtime unavailable`；重跑同一命令又完全正常。多批连跑均能复现，
单批命中率约 1/3～1/6 —— 典型的时序竞态。

**根因**：`FunASRProvider.runtime` 是**每次调用都查注册中心**的计算属性：

```swift
private var runtime: FunASRRuntime { FunASRRuntimeRegistry.current() }
```

而注册中心有**两个**调用点：窗口 `onAppear`（`WhisperASRApp`）与评测入口
（`ASRBench`）。`register()` 直接覆盖 `backend`，于是：

```
t0  评测入口 register(实例A)
t1  实例A 加载模型成功          ← 日志：SenseVoice-Small loaded
t2  窗口 onAppear register(实例B)  ← 覆盖！实例B 是空的、未加载
t3  transcribe 读到实例B → loadedType=nil → "runtime unavailable"
```

实测捕获的失败时序（t1→t2 间隔仅 **90ms**）：

```
RUNTIME-PROBE load on instance ObjectIdentifier(0x000000075582c730)   ← A 加载
RUNTIME-PROBE register available=true                                  ← B 覆盖
错误：Transcription failed: FunASR runtime unavailable
```

**修复**（`FunASRRuntime.swift`）：注册改为**幂等** —— 首个真实后端注册后，
后续注册直接返回，不覆盖已承载模型的实例。

```swift
static func register(_ runtime: FunASRRuntime) {
    lock.withLock {
        guard backend is PlaceholderFunASRRuntime else { return }
        backend = runtime
    }
}
```

**验证**：修复前多批连跑反复命中该失败（3 次连跑中 1 次失败；另一批 6 次连跑中
1 次失败），且失败位置随机、失败批次整体全灭 —— 符合竞态特征；
**修复后连跑 20 次全部通过（20/20）**，样本数与耗时一致，无残留抖动。

> 影响面：这不仅是评测工具的问题 —— 真实使用中若用户在模型加载瞬间切换窗口/触发
> 重绘，同样会命中该竞态，表现为"模型明明下载好了却报不可用"。属**用户可见缺陷**。

### 5.2 【已修复】评分器把「三点」与「3点」互判为全错

**现象**：`zh_long`/`zh_trad` 中正确的"三点"被记为错误。

**根因**：归一化函数把「点」**无条件**当作小数点并入数词缓冲：

```
「三点」→ 3         （点被当小数点吞掉，后面没有小数位）
「3点」→ 30        （点被当小数点，把点后的空串拼成 "0"）
→ 两种正确写法互相判成 100% 错误
```

**修复**（`ASRBench.swift`）：仅当「点」**夹在数字之间**时才作小数点
（`十二点五` → 12.5），否则视为正文（钟点用法）。

**验证**：新增回归测试 `testClockTimeDianIsNotDecimalPoint`，
覆盖"三点/3点"、"二十六度/26度"（钟点类，须等价）与"十二点五/12.5"（小数类，须等价）。
测试总数 330 → **331，全通过**。

**修复后 `zh_long`/`zh_short` 的 CER 从 2.8% 降到 0.0%**，全局 CER：
SenseVoice 6.2%→4.7%、whisper-medium 4.4%→3.8%。

## 六、发现的待决问题（未修改）

### 6.1 whisper 与 FunASR 共用 `selectedModelFile`，导致切换引擎需改用户配置

`FunASRProvider` 解析模型目录时走的是**与 whisper 同一个** `ModelPathResolver`：

```swift
private func modelDirectory() -> URL {
    URL(fileURLWithPath: ModelPathResolver.resolveModelPath(), isDirectory: true)
}
```

而 `selectedModelFile` 单键单值。因此：**只要当前选中的是 whisper 模型
（如 `ggml-medium.bin`），`--asr-engines funasr` 必然报"模型缺失"** ——
它拿到的是 `.bin` 文件路径，不是 FunASR 目录。

本次测试通过临时改写 `selectedModelFile` 绕开（测毕已还原）。
**建议**：为 FunASR 引入独立的选择键（如 `selectedFunASRModel`），
或让 `resolveModelPath()` 按引擎分派。这属于产品行为改动，未擅自实施。

### 6.2 评分器未归一英文数词

见 3.4。中文侧已归一，英文侧缺失，导致语义正确的 "12.5%" 记成 19% 错误。
**建议**：补一个英文数词→阿拉伯数字的归一（`twelve point five percent` → `12.5%`），
否则英文样本的正确率评估会系统性偏低。

### 6.3 googleV2 优选端点持续 429

`translate_a` 端点被 Google 反滥用拦截，全程回落。当前出口 IP 段如此。
代码已能自动回落并给出准确提示，**行为正确**；但需注意
**googleV2 的标签"优选端点"在当下环境名不副实**，评估时勿把它当作快通道。

### 6.4 实时链路对大模型不友好

whisper-medium 实时 RTF 3.78，意味着录音 1 分钟需约 3.8 分钟才能转完，
**字幕必然无限积压**。若产品要在实时场景提供 whisper，需要：
- 为实时场景强制选小模型（如 small 或专用 live 模型），或
- 引入增量/流式 whisper 变体（当前是每轮全量重转）。

|---|---|---|
| **实时字幕（默认）** | SenseVoice + googleV1 | RTF 0.15，端到端 ~1.1s，CER 4.7% |

## 八、复现方式

```bash
# 1. 构建（注意：需 Xcode 工具链）
cd /Users/hyj/Desktop/whisperASR_副本
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer swift build

# 2. 更新 bundle（裸二进制无 bundle id，读不到模型与配置）

# 3. 生成样本（本次用的 TTS 样本 + 参考清单）

afconvert -f WAVE -d LEI16@16000 -c 1 /tmp/r.aiff /tmp/asrbench/audio/zh_long.wav
# （其余样本同理，见本报告 2.1 节表格）

# 4. 跑矩阵（app 会把 stdout 重定向到 ~/Library/Logs/WhisperASR/app.log）
SonicScribe.app/Contents/MacOS/SonicScribe \
  --asr-bench /tmp/asrbench/audio \
  --asr-engines whisper,funasr \
  --translate-modes off,googleV1,googleV2,microsoft \
  --manifest /tmp/asrbench/manifest.json \
  --json /tmp/asrbench/out/result.json

# 加 --live 走实时分块链路（评估实时体验必须加）
```

**注意事项**：
- 切换 `whisper`/`funasr` 前需改 `selectedModelFile`（见 6.1）：
  `defaults write com.sonicscribe.app selectedModelFile "<模型目录名或文件名>"`
- 裸二进制**不能**跑评测（无 bundle id → UserDefaults 域为空 → 报模型缺失），必须经 `.app`。

## 九、附：测试覆盖与局限

**已覆盖**：3 套本地引擎 × {文件, 实时} × 5 样本；3 条翻译通道 × 2 个方向；
简繁归一；用户提示词开关（`asrPromptEnabled` 0/1）。

**未覆盖**：
- Apple Speech / Nemotron / Qwen3 / Online / Remote 引擎（模型未下载或需授权；
  Qwen3 的 `.gguf` 是 32 字节占位文件，Nemotron 未安装）
- paraformer-streaming / paraformer-zh（目录文件名为修复前的截断产物，
  见 `ModelDownloader` 的 `dropFirst` 修复注释，属陈旧下载残留，需重新下载后补测）
- 真实人声/噪声环境（本次为清晰 TTS 音源，CER 偏乐观，实际场景会上浮）
- 长音频（最长 9.3s，未验证 5 分钟级会议转录的内存与耗时曲线）

**实时链路为近似模拟**：ASRBench 的 `--live` 按固定 1s 步长喂入、末尾重发 tail，
不复刻 `ASRManager` 的自适应逻辑与真实录音时钟。结论用于横向对比，
绝对值可能略优于真实录音场景。
